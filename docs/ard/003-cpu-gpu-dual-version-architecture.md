## 背景 (Context)
1. 為了相容不同硬體環境，同一個演算法必須同時具備「純 CPU 運算版本」與「GPU 加速版本」。
2. 當前活躍開發者（我）思維上習慣於**暴力的序列迴圈（Sequential Loop）**若為使用**資料平行處理（Data Parallelism）**優化算法將大量**拖延MVP產出**
- 在規劃系統架構時，必須同時解決以下挑戰：
    - 雙版本切換機制： 如何在不增加執行期（Runtime）判斷開銷的前提下，優雅地切換 CPU 與 GPU 實作？
    - 認知負荷： 隨著演算法增加，如何避免單一資料夾內檔案破百，導致人類查閱與修改困難？

## 決策 (Decision)
- 決策一：編譯期宏決定（Compile-time Macro Switch）
    - 作法： 放棄執行期（Runtime）的 if-else 分支判斷，改由 CMake 在編譯期（Compile-time）透過 **演算法層級的編譯定義**來決定要建置哪一個版本。
    - 理由： 確保在純 CPU 環境部署時，執行檔也可以如預期運作。

- 決策二：演算法原始碼就地內聚（Co-location）
    - 作法： 將 Shader（.vert / .frag）的身份定義為 **「原始碼（Source）」** 而非 **「資產（Assets）」**。每個獨立演算法擁有自己專屬的微型資料夾（子目錄）。該演算法的對外標頭檔、CPU 實作、GPU 驅動實作、以及對應的 GLSL 檔案，必須通通放在同一個資料夾下。
    - 理由： 較**方便查改**


## 後果 (Consequences)
### 好處 (Pros) 
1. 硬體相容性： 在沒有 GPU 支援的環境中，仍可使用 CPU 實作執行演算法。
2. 開發彈性： 開發初期可以先以序列迴圈完成演算法，避免過早投入資料平行化而延誤 MVP。
3. 可讀性：演算法相關實作集中管理，方便人類查閱與修改。
4. AI Agent 友善性：AI Agent 只要執行一次目錄訪問（如 ls 或讀取該目錄），就能同時獲取該演算法的所有實作維度，大幅提升自動化重構與審查的準確度。
### 缺點與風險 (Cons) 
1. 與傳統 Shader 資產管理方式不同： 傳統圖形專案可能將 Shader 集中管理於獨立的 Assets/Shaders 目錄。本決策選擇以演算法為單位組織 Shader 原始碼，可能增加跨演算法共用 Shader 程式碼的管理成本。
2. 建置配置複雜度： 演算法數量增加時，需要維護各演算法的硬體實作選擇及對應的 CMake 建置配置。
3. 硬體資訊依賴： 編譯期選擇需要正確提供目標部署環境的 GPU 支援資訊，不能直接將開發機的硬體能力視為部署環境的硬體能力。
4. 實作一致性成本： CPU 與 GPU 版本必須維持相同的演算法語義及輸入輸出契約，否則可能產生硬體版本間的結果差異。
